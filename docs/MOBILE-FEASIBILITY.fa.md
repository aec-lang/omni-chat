# امکان‌سنجی OmniChat روی Android و iOS

تاریخ بررسی: ۲۰۲۶-۱۱-۰۲ · نسخهٔ بررسی‌شده: `fa85d04`

## نتیجه

چت روی Android و iOS با همین پایهٔ React و Capacitor قابل توسعه است و به بازنویسی کامل رابط نیاز ندارد. عامل چندمرحله‌ای با ابزارهای مشخص داخل برنامه یا روی یک سرور نیز روی هر دو پلتفرم شدنی است. کنترل خودمختار همهٔ برنامه‌های گوشی، هدف متفاوتی است و نباید آن را معادل افزودن tool calling به چت دانست.

| قابلیت هدف | Android | iOS |
|---|---|---|
| چت متنی استریم با API | مسیر موجود؛ نیازمند تست واقعی دستگاه | قابل افزودن با Capacitor iOS و تست دستگاه |
| تولید تصویر و تبدیل متن به صوت | مسیر API موجود؛ وابسته به سرویس | همان منطق قابل استفاده؛ ذخیره و اشتراک‌گذاری نیازمند بررسی بومی |
| دریافت فایل انتخاب‌شده توسط کاربر | با انتخاب‌گر و مجوزهای مربوط | با انتخاب‌گر Files و دسترسی مجاز |
| عامل داخل OmniChat | قابل ساخت | قابل ساخت |
| ابزارهای HTTP و اتصال به عامل روی سرور | قابل ساخت | قابل ساخت |
| کنترل رابط برنامه‌های دیگر | قابلیت‌های فنی محدود با کد بومی؛ محدودیت جدی انتشار در Play | دسترسی عمومی مشابه عامل دسکتاپ در مسیر معمول App Store وجود ندارد |
| اجرای بی‌وقفهٔ عامل پس از بسته‌شدن برنامه | نیازمند طراحی مخصوص محدودیت‌های پس‌زمینه | نباید فرض شود؛ برای کار طولانی، اجرای سروری مناسب‌تر است |

«قابل ساخت» در این جدول به معنی پیاده‌سازی یا آزمون‌شدن آن در نسخهٔ فعلی نیست.

## آنچه واقعاً در سورس وجود دارد

- رابط React با فارسی/انگلیسی، مدیریت مکالمه، تنظیمات سرویس و کتابخانهٔ پرامپت.
- درخواست مدل‌ها و چت استریم، تولید تصویر، تبدیل متن به صوت و مسیر تولید ویدئو در `src/hooks/useApi.js`.
- نگهداری داده‌ها و کلیدهای API در LocalStorage، در `src/contexts/AppContext.jsx`.
- Capacitor 6 برای Android؛ پروژهٔ بومی Android در هر اجرای CI تولید می‌شود.
- ساخت وب، انتشار Pages و ساخت APK آزمایشی در `.github/workflows/build.yml`.
- manifest و service worker برای مسیر وب نصب‌شدنی.
- ۱۵ تست موجود با `npm test` در این بررسی موفق شدند. این تست‌ها، آزمون UI، اتصال واقعی به مدل یا اجرای دستگاه iOS نیستند.

## کمبودها برای نسخهٔ موبایل جدی

### ۱. iOS هنوز اضافه نشده است

در `package.json` نه `@capacitor/ios` وجود دارد و نه دستورهای `ios:add`، `ios:sync` و ساخت iOS. هیچ job مربوط به Xcode نیز در CI وجود ندارد. وجود Capacitor Android به‌تنهایی خروجی iPhone ایجاد نمی‌کند.

باید بستهٔ iOS هم‌نسخه با خانوادهٔ Capacitor انتخاب شود یا همهٔ بسته‌های Capacitor با هم ارتقا پیدا کنند. نصب بی‌بررسی آخرین `@capacitor/ios` کنار نسخهٔ ۶ فعلی راه مناسبی نیست.

### ۲. موتور عامل وجود ندارد

بدنهٔ درخواست چت فقط مدل، پیام‌ها، استریم و دما را می‌فرستد. تعریف ابزارها، تجمیع `tool_calls` در استریم، اجرای ابزار و ارسال نتیجه به مدل پیاده‌سازی نشده است. تاریخچه نیز اکنون به `role` و `content` محدود می‌شود؛ اطلاعاتی مثل `tool_call_id` را نگه نمی‌دارد.

افزودن یک system prompt با عنوان «عامل» این قسمت‌های اجرایی را جایگزین نمی‌کند.

### ۳. ذخیره‌سازی و شبکه نیازمند تطبیق موبایل‌اند

- کلیدها برای نسخهٔ بومی باید به ذخیره‌سازی امن مبتنی بر Keychain در iOS و Keystore در Android منتقل شوند؛ Preferences ساده جایگزین مخزن امن نیست.
- مکالمه و فایل‌های رسانه‌ای بهتر است از LocalStorage جدا شوند؛ IndexedDB یا SQLite و فایل‌سیستم برنامه گزینه‌های قابل بررسی‌اند. مهاجرت داده‌های قبلی باید حفظ شود.
- درخواست‌ها اکنون از `fetch` وب استفاده می‌کنند. باید روی WKWebView و Android WebView، CORS، TLS، قطع شبکه، لغو درخواست و استریم آزمایش شوند.
- اگر انتقال HTTP بومی انتخاب شد، پشتیبانی واقعی استریم باید بررسی شود؛ جایگزینی سادهٔ `fetch` ممکن است جریان توکن‌ها را به پاسخ یک‌جا تبدیل کند.
- خروجی فایل اکنون با لینک دانلود مرورگر انجام می‌شود؛ مسیر Files/Share برای نسخهٔ موبایل باید آزمایش یا اضافه شود.
- `allowNavigation: ["*"]`، mixed content و debugging فعال در تنظیمات فعلی، باید برای نسخهٔ انتشار بازبینی شوند. مرور وب بیرونی نباید به‌طور نامحدود وارد WebView دارای پل بومی شود.
- lockfile در مخزن نیست و CI از `npm install` استفاده می‌کند؛ برای تکرارپذیری ساخت، ثبت lockfile و استفاده از `npm ci` پیشنهاد می‌شود.

## عامل پیشنهادی برای نسخهٔ اول

چرخهٔ عامل: درخواست کاربر ← پاسخ مدل یا فراخوانی ابزار ← بررسی آرگومان و مجوز ← اجرای ابزار ← بازگرداندن نتیجه به مدل ← پاسخ نهایی.

ابزارهای اولیهٔ پیشنهادی:

1. جست‌وجو در مکالمه‌ها و یادداشت‌های خود OmniChat.
2. خواندن سندی که کاربر صریحاً انتخاب کرده است.
3. ساخت خروجی متنی یا فایل و نمایش پیش‌نمایش پیش از ذخیره یا اشتراک‌گذاری.
4. فراخوانی سرویس‌های HTTP تعریف‌شده، با احراز هویت و دامنهٔ مجاز.
5. ابزارهای تقویم، یادآور یا عکس، فقط با افزونهٔ بومی و مجوز مربوط و تأیید تغییرات.

برای هر ابزار باید نام و schema ثابت، اعتبارسنجی آرگومان‌ها، مجوز متناسب، محدودیت زمان، محدودیت تعداد گام، لغو اجرا و گزارش فعالیت وجود داشته باشد. مجوزهای برنامه را نباید صرفاً با دستور مدل افزایش داد. مدل انتخابی نیز باید فراخوانی ابزار را پشتیبانی کند.

برای اجرای کارهای طولانی، عامل می‌تواند روی سرور اجرا شود و گوشی وضعیت و نتیجه را دریافت کند. اتصال OmniChat به یک عامل دسکتاپ مانند Atlas نیز مسیر توسعهٔ جداگانه‌ای است؛ چنین اتصال آماده‌ای در این سورس وجود ندارد.

## مرزهای سیستم‌عامل و انتشار

### iOS

قواعد App Store استفاده از API عمومی و ماندن در محدودهٔ مجاز برنامه را الزام می‌کنند؛ بخش‌های 2.5.1 و 2.5.2 مرتبط‌اند. اجرای پس‌زمینه نیز طبق 2.5.4 به کاربردهای مجاز محدود است. بنابراین نباید قول عاملی داد که آزادانه وارد هر اپ شود، صفحه‌ها را بخواند و هر جا کلیک کند.

قابلیت‌های یکپارچه‌سازی رسمی، انتخاب فایل، اشتراک‌گذاری و ابزارهای دارای مجوز می‌توانند دامنهٔ کاربرد عامل را گسترش دهند. توانایی هر ابزار به API و مجوز همان قابلیت محدود خواهد بود.

### Android

برای خواندن برخی اجزای رابط و اجرای gesture در برنامه‌های دیگر، مسیرهای بومی مثل AccessibilityService وجود دارند؛ این پروژه فعلاً چنین سرویسی ندارد. از طرف دیگر، صفحهٔ رسمی Google Play دربارهٔ Accessibility، استفاده‌ای را که برنامه با آن خودمختارانه آغاز، برنامه‌ریزی و اجرا یا تصمیم‌گیری کند، ممنوع می‌داند؛ استثنای مشخصی برای ابزارهای تأییدشدهٔ کمک به افراد دارای معلولیت تعریف شده است. این استثنا را نمی‌توان برای یک چت‌بات عمومی فرض کرد.

توزیع مستقیم APK از بررسی Play عبور نمی‌کند، اما محدودیت‌های فنی و مجوزهای Android را حذف نمی‌کند. معماری نسخهٔ قابل انتشار در فروشگاه بهتر است بر ابزارهای API و مجوزهای مشخص استوار باشد.

## ساخت iOS در GitHub Actions

ساخت iOS را می‌توان در job مبتنی بر macOS و Xcode در GitHub Actions انجام داد؛ داشتن مک روی میز توسعه‌دهنده برای اجرای این job شرط نیست. دسترسی به آیفون برای آزمون واقعی همچنان لازم است.

دو خروجی باید تفکیک شوند:

- **ساخت آزمایشی شبیه‌ساز:** برای بررسی کامپایل و اجرای خودکار؛ فایل قابل نصب مستقیم روی آیفون نیست.
- **نسخهٔ قابل نصب و توزیع:** نیازمند تنظیم signing، تیم توسعه‌دهنده، شناسهٔ برنامه و provisioning متناسب با روش انتشار است. مسیر معمول آزمایش عمومی iOS، TestFlight است؛ ساخت فایل IPA بدون امضای مناسب، نصب عمومی مانند APK فراهم نمی‌کند.

معیار پذیرش نسخهٔ اول: اتصال واقعی به سرویس، دریافت توکن‌های استریم، لغو پاسخ، حفظ مکالمه پس از بازگشت به برنامه، رفتار کیبورد و safe area، ذخیره/اشتراک خروجی و مدیریت خطای شبکه روی Android و iPhone.

## ترتیب پیشنهادی اجرا

1. تثبیت نسخهٔ چت: شبکه، ذخیره‌سازی، کلید امن و خروجی فایل.
2. افزودن iOS و CI ساخت شبیه‌ساز؛ سپس signing و TestFlight پس از فراهم‌شدن حساب و تنظیمات لازم.
3. افزودن موتور عامل مشترک با ابزارهای داخل برنامه و سرویس‌های مشخص.
4. بررسی مستقل ابزارهای بومی هر سیستم‌عامل؛ نمایش قابلیت‌ها بر اساس پلتفرم و مجوز واقعی.
